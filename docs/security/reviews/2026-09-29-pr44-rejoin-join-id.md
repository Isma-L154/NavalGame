# Differential security review: rejoin after a lost join reply (#44)

**Date:** 2026-09-29 · **Scope:** `fix/rejoin-after-lost-reply` vs `main` · **Strategy:** DEEP (seat access: mandatory review per `CLAUDE.md`)

## Change

A fresh `join` may carry `join_id`, 32 random bytes generated by the browser (the same format as a seat token). The room stores only its SHA-256 hash with the seat. A later fresh join carrying the same id reclaims that seat. The server issues a **new** seat token, which invalidates the one that was lost. The id stops working once the player proves they received their token, either by reconnecting with it or by sending any seated message.

| File | Risk | Why |

| `src/naval/rooms/room.py` | HIGH | A second way to take a seat, next to the seat token |

## Findings

| # | Severity | Finding | Status |
|---|---|---|---|
| 1 | MEDIUM | As first written, the join id stayed a valid seat credential for the whole game when the connection never dropped (it was cleared only by a reconnect with the token). A first fix cleared it on any seated message but only saved that when the action succeeded. | Fixed: any seated message clears it (`token_delivered`), saved on its own before the action, so a refused action counts too. Messages arrive in order and the client sends nothing seated before `joined`, so a seated message proves the token arrived. Test: `test_a_join_id_stops_reclaiming_once_the_seat_acts` (with a refused action). |
| 2 | LOW | Whoever holds a live join id and uses the same nickname can take the seat and rotate its token, kicking the original socket (close 4000). The id is chosen by the client, so a third-party client could pick a guessable one. | Accepted: with the official client it has the entropy and exposure of a token (32 random bytes, TLS only, page memory only, hashed at rest, constant-time comparison). A weak id only endangers the seat of the client that chose it, and only between its join and its first seated message. |
| 3 | INFO | On a rollback, the previous server rejects `join` messages carrying `join_id` (`extra="forbid"`) from pages loaded before it, and cannot read rooms whose seat still has a `join_hash`. | Mitigated: `join_hash` is only written while set, so settled rooms stay readable. Pages recover on reload. Rooms expire after an hour idle. |

No HIGH findings.

## Evidence

- **Validation (control 3):** `join_id` must match `^[A-Za-z0-9_-]{43}$` (the token pattern). Malformed values are `invalid_message` (`tests/protocol/test_messages.py`).
- **Secrecy:** only `hash_token(join_id)` is stored; `test_join_ids_round_trip_as_hashes_only` asserts the raw id never appears in stored JSON. Comparison goes through `token_matches` (`hmac.compare_digest`).
- **Precedence:** a join with a `token` never looks at `join_id`. A join id that matches no seat falls through to a normal fresh join (a new seat, or `room_full`), so it cannot be used to probe seats.
- **Rotation:** a reclaim replaces `token_hash`, so the lost token can no longer reconnect (`test_a_fresh_join_repeated_with_its_join_id_gets_the_same_seat_back`).
- **Real Worker:** `test_a_join_whose_reply_was_lost_gets_its_seat_back`: the first socket's reply is dropped, the second join with the same id gets seat 0 back, and a third player still gets seat 1.
- **RLS equivalent (control 6):** views are unchanged; the per-seat view test still passes.

## Coverage limits

- The exact production race (the reply lost in flight) is simulated by closing the socket after the server answered, not by dropping packets.
